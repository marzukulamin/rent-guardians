# Ten-million-user review

Reviewed 9 October 2026 for the local Rent Guardian app. Code changes are applied and built. **This app is not certified for 10 million users.** Production infrastructure, service integrations and database redesigns below remain required. No deployment or production capacity test was performed.

## Traffic assumptions

Registered accounts are different from simultaneous users. Planning examples, not measured demand:

- 10 million accounts, 20% daily active, 30 API requests per active user: 60 million requests/day, approximately 694 requests/second on average; a 10x peak needs approximately 6,944 requests/second.
- 100,000 simultaneous active users making one request every 10 seconds: 10,000 requests/second. Ten million simultaneous users at that rate would need one million requests/second.
- 2 million daily visitors downloading 5 MB of media each: approximately 10 TB/day, before uploads, retries and backups. Public images need a CDN and resized variants.
- Monthly billing and payment reminders concentrate writes into short periods. Jobs must be measured separately from browsing.

|---|---|---|---|
| High | QA/demo UI and fixtures undermine trust | Header/footer, sample account buttons and prefilled shared password; marked seeded requests and inspections | **Applied:** removed demonstration chrome, blank real sign-in form, neutral customer copy; portal reads omit marked fixtures and linked fixture tenancy/invoice activity. Original records remain available to tests and authorized admin exploration. |
| High | Stock photography and generic 3D apartment could misrepresent a property | Public seed photos are not property-specific; one generic scene reused in detail pages | **Applied:** stock/generated photos show “Photos not yet available”; missing property tours show an unavailable state. Generic scene remains a landing-page illustration. Real property uploads/tours are still needed. |
| Critical | Single server saturates and becomes an outage point | Current launcher uses PHP's development server | **Template supplied, deployment pending:** `deploy/nginx.conf.example` routes APIs to PHP-FPM, adds TLS, compression, edge request limits and cache policy. Needs real domain, certificates, process supervision, autoscaling and redundant nodes. Nginx/PHP-FPM are not installed or validated here. |
| High | Anonymous browsing creates millions of session files | Bootstrap previously started a new session for every property/lookup/photo GET | **Applied:** cookie-free public discovery/media reads skip session creation. Session endpoint and authenticated reads retain session behavior. New API check confirms anonymous property reads send no session cookie. |
| High | Sessions disappear when requests move between servers | Bootstrap forced a local file directory | **Applied configuration support:** honors PHP's configured session handler; supports `RG_SESSION_HANDLER` and `RG_SESSION_PATH`, and fails when sessions cannot start. **Pending:** deploy redundant shared session storage, install its PHP extension, configure locking/expiry, and test failover. |
| High | API/login/signup/upload abuse consumes CPU, storage and connections | Coarse login IP lockout; no shared successful-write/upload budgets | **Applied:** atomic database-backed budgets for writes (180/min/user), login (100/15 min/IP and 20/15 min/identity), registration (10/15 min/IP), uploads (60/hour/user). Failed login history now checks indexed identity instead of penalizing every person on a shared IP. 429 includes Retry-After. Tune budgets using real traffic; database budgets alone cannot withstand a flood. |
| High | Oversized JSON exhausts PHP memory | Unbounded `php://input` reads | **Applied:** JSON body capped at 1 MiB, including bounded reads when Content-Length is absent; malformed JSON returns 400. Upload bytes retain their separate 10 MB file limit. Nginx template rejects oversized input before PHP. |
| High | Traffic counter storage grows without bounds | Every budget window adds counters | **Applied cleanup command:** `server/clean-request-budgets.php`, indexed expiry and bounded 5,000-row deletes, at most 100,000 per invocation. **Pending:** schedule every five minutes and alert on growing backlog. No scheduler was installed. |
| High | Failed-login checks scan history | Identity checks need an index ordered by time | **Applied:** repeatable migration adds `(identity_hash,attempted_at)`. Counters and indexes are installed locally; new setup installs them too. Use a controlled DDL rollout on production-sized tables. |
| High | Repeated static downloads waste bandwidth | Local router provided no cache policy for hashed bundles | **Applied:** immutable one-year cache for hashed `/assets/`, short cache for other assets, revalidated HTML. Private API/document responses stay private. Template adds gzip; a real CDN still needs configuration. |
| Medium | Large 3D library delays frontend startup | Three.js imported synchronously from landing/workspace modules | **Applied:** lazy scene boundary moves the illustration and Three.js out of the main entry bundle. React routes and workspace data still need further splitting and route-specific requests. |
| High | Healthy-looking processes hide DB outages | No dedicated readiness route | **Applied:** `/health/ready` checks database connectivity without a session and returns 503 on failure. Production template keeps it private. **Pending:** actual load-balancer probes, dependency metrics and incident alerting. |
| Critical | Catalog/provider/location startup payload grows with the entire marketplace | `lookups` still reads whole tables; providers/meal plans/products downloaded together | **Open redesign:** separate stable small lookups, cursor-paginated product/meal/provider endpoints, searchable provider selectors and route-specific loading. Preserve carts across pages and validate IDs/prices on the server. Adding arbitrary caps would hide available services. |
| Critical | Staff dashboards omit older tasks and overload browsers | 200-row caps without navigation; several subscriptions/visits/referrals/selectors remain unbounded | **Open redesign:** separately paginated work queues with authorization independent of the displayed tenancy page, scoped totals and searchable assignments. Existing batched child queries reduce round trips but do not solve this. |
| High | Deep search pages and substring filters become expensive | OFFSET, exact COUNT, location `%term%`, and correlated photo/permission reads | **Open redesign:** cursor navigation with deterministic sort ties, indexed location IDs, search index where needed, query-plan benchmarks and selective caching. Portal fixture predicates are temporary presentation isolation and add filtering cost. Production must use a separate clean dataset. |
| High | Nearby-provider discovery evaluates too many distances | Provider workspace calculates distances over eligible requests | **Open redesign:** indexed geographic bounding/geospatial candidates before distance computation, paged job feeds and candidate-count monitoring. Claim authorization must remain checked transactionally. |
| Critical | Database connection exhaustion and broad reporting scans | One PDO connection per request; admin counts every table and sums all balances/payments | **Open infrastructure/application work:** bounded PHP worker pools, database connection budget, precomputed reporting snapshots, read replicas for appropriate reads, query timeouts and slow-query monitoring. Profile with 10-million-scale distributions before considering partitioning/sharding. |
| Critical | Uploaded files vanish across nodes or fill disk | Private files remain local; full-size photographs served through PHP | **Open integration:** private object storage, authorization-preserving download links, public thumbnail pipeline/CDN, user byte quotas, scanning, lifecycle/retention rules and upload-backup restoration. Existing MIME/size checks and upload rate limits are only part of this. |
| Critical | Retried submissions can duplicate business operations | Timeout messaging discourages replay, but generic idempotency keys are absent | **Open redesign:** user/operation-scoped idempotency keys and atomic request/result storage for orders, payments and other charge-producing actions. Verify simultaneous workers; current HTTP server serializes execution. Existing locks and unique invoice/job keys are retained. |
| Critical | Billing spikes and external deliveries block operational throughput | Current jobs are bounded/idempotent, but one runner handles all monthly work; no external delivery queue | **Open redesign:** partitioned job queues, transactional outbox, deduplicated consumers, bounded retries/dead-letter handling and backpressure. Measure billing duration, backlog and payment callback spikes. |
| Critical | Downtime, lost records or compromise go unnoticed | No verified failover, off-host backup/restore drills, production alerts or actual verification provider | **Open operations/integrations:** encrypted backups of DB and uploads, restore drills, recovery targets, credential rotation, HTTPS, registration verification, retention policy and incident response. Real payment/SMS/push/dispatch connections and staffing must be supplied. |

## Local verification

- Existing regression suite: 21/21 passed, including CSRF, permissions, privacy, billing, maintenance and separate payment approvals.
- Two additional API checks passed: anonymous discovery/session behavior, fixture listing omission, readiness and oversized JSON rejection. Existing unit/fetch checks also passed after the last changes.
- `tools/portal-traffic-test.php`: fixture/linked-payment isolation, budget rejection at the threshold, and counter visibility across separate database connections passed. It removes only its own random counter after testing. This is not a simultaneous-worker stress test.
- Production build passed. All 25 server PHP files passed final syntax checks.
- `tools/production-portal-qa.cjs`: visible guest copy, empty sign-in inputs, listing/API consistency, desktop/mobile screenshots and no browser errors passed. Screenshots: `storage/production-portal-desktop.png`, `storage/production-portal-mobile.png`.
- Existing mobile portal check passed on 26 routes across eight roles at 390 px, without horizontal overflow or browser errors.
- Read-only local probe: **200 requests, 20 workers, zero failures, 41 requests/second, p95 545 ms, p99 570 ms**. See `docs/scale-http-results.json`. This tiny development-server measurement cannot establish production throughput or 10-million-user capacity.

## Production work sequence

1. Provision staging with PHP-FPM/Nginx, shared sessions, object storage, CDN, database observability and backup/restore. Configure the real domain and TLS; validate the supplied Nginx template. Set configuration environment to `production` so secure session cookies are enforced behind TLS termination. Trust forwarding headers only from configured proxies; app budgets currently use REMOTE_ADDR.
2. Isolate customer data from tests/seeds, rotate local/shared credentials, and onboard verified real providers/listings. Presentation filtering is not deletion or proof that seeded accounts are real. Mixed fixture invoices are omitted as a whole so altered child lists are not shown beside misleading totals; rewards/admin aggregates can still include underlying fixtures.
3. Implement the catalog, workspace, reporting, geographic-search and idempotency redesigns above; add real integrations and job queues. Schedule both business jobs and counter cleanup. A shared Redis handler requires an installed extension and locking configuration; setting an environment variable alone is insufficient.
4. Test staged datasets with 10 million accounts and representative listings, payment histories, photos, providers and audit records. Synthetic accounts alone do not represent the workload. Include realistic location skew and large household/business accounts.
5. Run public reads, authenticated reads, writes, uploads and billing jobs separately and together. Increase traffic gradually; measure achieved throughput, p95/p99, errors, database CPU/connections/locks, session latency, queue age, memory and bandwidth. Test burst traffic, duplicate submissions, dependency outages and node failover. Define latency/error/recovery targets before acceptance.
6. Approve a production rollout only after measured targets pass. Public hosting, capacity procurement, payment contracts and migration of real data have not been performed by this change.
