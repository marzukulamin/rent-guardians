# Rent Guardian implementation report — 9 October 2026 (Asia/Dhaka)

This report distinguishes new changes from the existing app. The entire V1.0 source story extraction (161 stories) was read and compared with its source DOCX. The React/Vite, PHP/PDO and MariaDB architecture was retained. No production deployment or live payment was made. Acceptance of the complete master prompt remains PARTIALLY COMPLETED.

## A. Actual changes

- All portals: shared 18 px desktop and 17 px mobile body text, 16 px secondary text, 30–32 px page headings, visible focus rings and practical 44 px controls. Cards, forms, tables, review screens and navigation reflow on narrow screens.
- Owner/tenant listing capability: private database drafts, recovery after reload, a review step, listing preview, no invented bedroom or size defaults, retained included utilities during editing, and readable View details actions. Publication is rejected while a tenancy/application remains open.
- Property photography: no unrelated fallback for absent photos; explicit demo labels; multi-file selection, previews, browser WebP conversion capped at 2400 px, categories/captions, cover selection, ordered navigation, thumbnails, touch swipe, fullscreen controls and archived removal. Server checks image MIME, actual dimensions, 10 MB and 40 megapixel limits, 30 active photos and ownership. Removed uploads cannot be fetched from their file routes.
- Tenant privacy: public results conceal exact house/road/floor/flat and coordinates; confirmed viewing participants, owners, assigned agents and authorized tenancy participants retain appropriate access. Uploads must reference the same property as their tenancy.
- Renting: fixed the reserved-property verification upload permission; advance invoices are separate and due on move-in; unrelated paid invoices cannot satisfy the advance; repeated activation is rejected; approved police documents must belong to the designated head tenant. Move-out cannot close before its recorded date.
- Finance/services: BDT fractional amounts remain visible, paid orders require a reviewed refund/adjustment before cancellation, and catering enrollment requires an active tenancy and verified active provider.
- Search: independent server filters for division/district/area/sub-area, paginated results in groups of 24, and protection against stale search responses.

## B. UI verification

The browser suite checks guest discovery, filtering, property reports, conceptual-model controls, tenant routes, owner listing access, provider tabs, supervisor, finance, field agent, and every administrator tab. The priority suite additionally exercises draft persistence, listing review/submission, the absent-photo state, optimized upload/removal and readable text at 375, 390, 768, 1024 and 1440 pixels. The mobile portal suite checks 26 routes across eight roles at 390 pixels. Tablet caption and signed-in header overflow were found and repaired. See verification.md for final command outcomes.

## C. Database changes

`server/migrate.php` safely adds `property_photos.category`, nullable `deleted_at`, and `photo_order(property_id,deleted_at,sort_order,id)`. It creates `listing_drafts`, keyed by user with a foreign key, JSON text payload and update timestamp. The user_stories implementation_status field now supports the five requested audit statuses, preserving source story text and conservatively replacing older heuristic labels. The schema for fresh setup contains the same structures. Existing properties, photo bytes, documents and historical financial records are preserved. Upload and photo ordering changes use transactions and parent-row locks. New advance invoices reuse the existing unique invoice billing-group model. No resets or destructive production migrations were performed.

## G. Remaining work and dependencies

- Authentic property photographs, actual tour media and verified real listing data have not been supplied.
- Live bKash/cards, SMS, phone, push, bank transfer verification and provider/owner payouts are not configured. Only explicit manual review/confirmation is operational.
- The agreement is a sample typed-consent template; reviewed real agreements and an appropriate production signing integration are still needed. Police/identity records are reviewed locally, without a real external identity check.
- Inspection repair decisions do not yet generate a complete owner-approved provider repair/invoice chain automatically.
- Catering subscriptions/rosters exist; daily delivery records, outcome confirmation, cancellation/refund adjustments and recurring fulfillment remain incomplete. Grocery customer confirmation and inventory/stock controls need extension.
- Move-out notice and inspection timing work; deposit refunds, adjustments, damage agreement and final settlement are incomplete. Head-tenant transfer requires further contract and financial reassignment verification.
- Cross-role room listings require a dedicated authority/owner-consent workflow. Provider-specific navigation, customer cancellation, appointment slot capacity, declines and urgent escalation need further implementation.
- Complete browser journeys for grocery and catering providers, role matrix tests, OTP expiry/lockout boundaries, referral rules and scheduler idempotency still need expanded coverage.
- Scheduled jobs run manually/startup; install a reliable production scheduler, HTTPS, backups, retention policies and production operational monitoring before public use.
